# MiniPaaS 持久化反向代理路由

## 管理方式

在“应用”页面打开目标网站的“反向代理路由”，可以为同一网站添加多条路径路由。路由按排序数字从小到大生成，并始终位于网站 Service 的普通 `handle` 之前，因此不会被 SPA fallback 截获。

每条路由支持启停、路径前缀、HTTP/HTTPS 上游、去除路径前缀、上游 Host、WebSocket/SSE/流式响应以及自定义请求头。Caddy 原生支持 WebSocket；启用流式模式时会生成 `flush_interval -1`。

## 多应用隔离

- 每条代理路由和订阅路由都必须绑定唯一 `appId`；应用、域名、上游、Host、Supabase Project ID 和排序均按应用保存。
- 没有配置代理的应用不会自动获得 `/supabase`。系统没有供所有网站共用的全局 `SUPABASE_URL`。
- Supabase 类型路由的 Project ID 必须与该路由上游的 `project.supabase.co` 主机一致，否则保存会被拒绝。
- 修改、部署、回滚或删除应用时，只改变该应用的持久化路由块；其他应用的路由块保持不变。
- 应用域名、订阅域名或同一应用的启用路径发生冲突时，后台会阻止保存并指出冲突。
- 后台可以读取当前应用自己的 `VITE_SUPABASE_URL` 或 `VITE_SUPABASE_PROJECT_ID` 作为建议值，但不会自动使用；管理员必须点击确认。系统不会读取其他应用的变量。
- 当多个应用都启用订阅代理时，只生成各自的明确域名路由，不生成可能串项目的全局动态 catch-all。

## 安全应用流程

1. MiniPaaS 校验路径、域名、上游和请求头。
2. DNS 解析上游，拒绝 localhost、私有网段、链路本地地址、Kubernetes Service 和云元数据地址。
3. 将当前 Caddy ConfigMap 备份到 `/var/lib/minipaas/caddy-backups`。
4. 在运行中的 Caddy 容器内执行 `caddy validate`。
5. 仅在配置发生变化且验证成功时更新 ConfigMap、滚动重启 Caddy。
6. 滚动更新失败时自动恢复旧 ConfigMap。

## 持久化与恢复

路由保存在 `/var/lib/minipaas/state.json` 的应用 `proxyRoutes` 字段，每条记录都含 `appId`。订阅路由保存在 `subscriptionRoutes`，同样包含 `appId` 和 Supabase Project ID；不属于应用的原有 Caddy 块保存在 `caddyBaseConfigs`。这些内容都包含在 MiniPaaS 控制平面备份中。

MiniPaaS 启动 30 秒后会自动对账 Caddy 配置，之后每 10 分钟检查一次。应用部署、重新部署、回滚、域名修改和删除应用后也会重新生成。因此恢复 `state.json`、`master.key` 和应用资源后，路由会自动恢复。

也可以在路由页面点击“导出配置”下载 JSON；新环境中进入对应应用，点击“恢复配置”上传 JSON。导出文件保留 `appId` 绑定，导入到其他应用会被拒绝，恢复仍会执行完整安全校验。

## 迁移验收

迁移后依次检查：

1. MiniPaaS 的应用、域名与代理路由是否可见。
2. 点击“一键健康检查”。
3. 访问 `/supabase/rest/v1/`，未带 apikey 应得到 Supabase 401 JSON。
4. 检查用户登录、管理员登录和 `traffic-stream` SSE。
5. 用真实 UUID 检查订阅地址。
6. 重新部署或回滚应用，再重复上述检查。
